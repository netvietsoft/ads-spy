DEVELOPMENT WORKSPACE STANDARD
=================================

Mục tiêu
--------
Xây dựng một cấu trúc dự án chuẩn để nhiều AI Agent như Claude Code, Codex, DeepSeek, Aider,
Cline, Roo Code... có thể cùng tham gia phát triển một dự án mà:

- Không đạp chân nhau.
- Không tự ý phá kiến trúc.
- Không sửa test để "làm xanh".
- Có phân công nhiệm vụ rõ ràng.
- Có trạng thái dự án rõ ràng.
- Có cơ chế rollback bằng Git.
- Có test/review/security gate trước khi merge.
- Có lịch sử đầy đủ mọi thay đổi.
- Có thể mở rộng thành AI Coworker Project Mesh / AI Development Platform.

2. VAI TRÒ CỦA CÁC FILE GỐC
======================================================================

README.md
---------
Tài liệu giới thiệu dự án.

Bao gồm:
- Project là gì.
- Mục tiêu dự án.
- Tech stack.
- Cách setup.
- Cách chạy.
- Link tới rules.
- Link tới Architecture.
- Link tới Workflow.
- Link tới Testing.
- Link tới Deployment.


AGENTS.md
---------
Đây là "HIẾN PHÁP" dành cho tất cả AI Agent.

Mọi Agent bắt buộc đọc trước khi code.

Thứ tự bắt buộc:

1. Đọc README.md
2. Đọc AGENTS.md
3. Đọc Docs/rules.md
4. Đọc Architecture liên quan
5. Đọc SPEC của task
6. Kiểm tra .ai/locks.json
7. Kiểm tra git status
8. Kiểm tra branch/worktree đang làm
9. Không sửa file ngoài phạm vi task
10. Không bắt đầu code nếu chưa hiểu acceptance criteria


CLAUDE.md
---------
File hướng dẫn riêng cho Claude Code.

Không nên copy toàn bộ luật.

Chỉ ghi:

- Claude phải đọc AGENTS.md.
- Claude phải đọc Docs/rules.md.
- Claude phải tuân theo Task ID.
- Claude phải kiểm tra file lock.
- Claude phải test trước khi commit.


.clinerules
-----------
File rule dành cho Cline / Roo Code.

Chỉ tham chiếu tới:
- AGENTS.md
- Docs/rules.md
- Docs/Architecture/
- Task hiện tại


Docs/rules.md
-------------
Chứa luật code chung cho toàn dự án:

- Framework sử dụng.
- Version framework.
- Naming convention.
- Folder convention.
- API convention.
- Database convention.
- Error handling convention.
- Logging convention.
- Test convention.
- Security convention.
- Dependency policy.
- Git convention.
- Deprecated libraries bị cấm.
- Coding style.
- Backend: [Tên framework, version, VD: Node.js 20, NestJS]
- Frontend: [VD: Next.js 14, App Router, TailwindCSS]
- Cấm tuyệt đối: Không dùng các thư viện đã deprecated (VD: moment.js -> dùng dayjs).
- Tên biến, hàm: camelCase. Tên class, component: PascalCase.
- Mọi hàm logic phức tạp đều phải có JSDoc hoặc docstring giải thích tham số đầu vào/ra.
- Nếu Agent gặp lỗi, BẮT BUỘC đọc file `bug_report.md` và kiểm tra lịch sử các lần sửa trước để không đi vào vết xe đổ.
- Nếu vướng mắc quá 3 lần, dừng lệnh, báo cáo `[NEED_HUMAN_INTERVENTION]`.
- Mọi commit phải theo định dạng: type(scope): subject.
- Tuyệt đối không thao tác trên nhánh main.

6. TASK PHẢI MACHINE-READABLE
======================================================================

Không dùng task dạng:

"làm payment"

Mỗi task phải có ID và metadata rõ ràng.

Ví dụ:

id: TASK-0154

title: Implement Stripe webhook

owner: agent-payment

status: running

priority: high

dependencies:
  - TASK-0151

files_allowed:
  - src/payment/**
  - tests/payment/**

files_forbidden:
  - src/auth/**
  - database/migrations/**

acceptance_criteria:
  - verifies Stripe signature
  - supports payment_intent.succeeded
  - supports payment_intent.failed
  - idempotent
  - unit tests pass

commands:
  test:
    - npm run test:payment
  lint:
    - npm run lint
  typecheck:
    - npm run typecheck

max_fix_cycles: 5


Trạng thái task:

backlog
ready
running
review
blocked
done

7. FILE LOCK / OWNERSHIP
======================================================================

Bắt buộc dùng:

.ai/locks.json

Ví dụ:

{
  "src/payment/**": {
    "agent": "payment-agent",
    "task": "TASK-154"
  }
}

Mọi Agent trước khi sửa file phải kiểm tra lock.

Nếu file bị lock:

LOCKED
DO NOT MODIFY

Nếu cần sửa file đã bị Agent khác giữ:
- Gửi request cho Orchestrator.
- Orchestrator quyết định handoff hoặc unlock.
- Không tự ý phá lock.

8. GIT LÀ BẮT BUỘC
======================================================================

Mỗi thay đổi phải có thể rollback.

Cấm code trực tiếp vào main.

Branch convention:

agent/backend/TASK-101
agent/frontend/TASK-102
agent/payment/TASK-103
agent/fixer/TASK-104


Khuyến nghị dùng Git Worktree:

main

worktrees/
├── backend-TASK-101
├── frontend-TASK-102
├── payment-TASK-103
├── test-TASK-104
└── designer-TASK-105


Mục đích:

- Nhiều AI Agent cùng code một repo.
- Không đạp filesystem.
- Giảm conflict.
- Dễ rollback.
- Dễ kiểm tra Agent nào thay đổi gì.

14. CẤM AI SỬA TEST ĐỂ LÀM XANH
======================================================================

Luật bắt buộc:

NEVER change expected test results merely to make tests pass.

NEVER:
- delete failing tests
- skip failing tests
- disable tests
- loosen assertions
- remove edge cases
- mock away real failures
- lower coverage threshold
- change acceptance criteria

trừ khi có approval rõ ràng.

17. DEPENDENCY POLICY
======================================================================

AI không được tùy tiện:

npm install xxx
pip install xxx
cargo add xxx
composer require xxx


Trước khi thêm dependency phải kiểm tra:

1. Project đã có thư viện tương tự chưa?
2. Có thể dùng standard library không?
3. Project còn maintained không?
4. Có deprecated không?
5. License là gì?
6. Có security issue không?
7. Bundle size / runtime cost?
8. Có ảnh hưởng architecture không?


Nếu dependency ảnh hưởng kiến trúc:

phải tạo ADR.


======================================================================
18. ADR - ARCHITECTURE DECISION RECORD
======================================================================

Mọi quyết định lớn phải ghi tại:

Docs/ADR/


Ví dụ:

ADR-027
Title:
Use Redis/BullMQ for payment jobs

Context:
Webhook processing có thể lâu.

Decision:
Dùng Redis + BullMQ.

Reason:
- Retry.
- Queue.
- Observability.
- Không block API.

Rejected:
- In-memory queue.
- Cron polling.

Impact:
- Cần Redis.
- Cần worker.
- Cần monitoring.

31. 20 LUẬT CỨNG DÀNH CHO TẤT CẢ AI AGENT
======================================================================

1. Never code without TASK ID.

2. Never modify files outside assigned task scope.

3. Never modify a locked file.

4. Never commit directly to main.

5. Never modify tests merely to make them pass.

6. Never delete failing tests.

7. Never skip/disable tests without explicit approval.

8. Never disable lint, typecheck or security checks.

9. Never install dependencies without justification.

10. Never alter architecture without ADR.

11. Never change database schema without migration.

12. Never expose secrets.

13. Never use destructive Git commands automatically.

14. Never git push --force.

15. Always run verification before checkpoint commit.

16. Always update task state.

17. Always update changelog for meaningful changes.

18. Always create handoff before ending an unfinished session.

19. Stop autonomous fix loop after configured maximum attempts.

20. If uncertain, inspect project state/code/docs first. Never invent project state.

35. TODOS & TASK STATE WORKFLOW (bổ sung 28/08/2026)
======================================================================

Nguồn sự thật của task là THƯ MỤC TRẠNG THÁI, không phải một file danh sách:

.ai/tasks/backlog/   chưa sẵn sàng
.ai/tasks/ready/     đủ điều kiện nhận
.ai/tasks/running/   đang làm (bắt buộc có owner)
.ai/tasks/review/    chờ review/quality gate
.ai/tasks/blocked/   kẹt (bắt buộc có blocked_reason)
.ai/tasks/done/      xong (đã qua Quality Gate §19)

TODOS.md ở PROJECT_ROOT là DASHBOARD SINH TỰ ĐỘNG — cấm sửa tay.

Workflow bắt buộc cho MỌI agent và người:

1. Đổi trạng thái  = git mv file YAML sang thư mục trạng thái mới.
2. Sửa nội dung    = sửa trực tiếp YAML (owner, notes, criteria đã đạt).
3. Tạo task mới    = thêm TASK-xxx.yaml vào backlog/ theo schema §6.
4. SAU MỌI thay đổi chạy:

   python scripts/update-todos.py

   Script sinh lại TODOS.md + cập nhật .ai/state.json (đếm task,
   vi phạm luật trạng thái). Commit task + 2 file sinh ra cùng nhau.

Luật cứng:
- running không owner  -> script báo vi phạm.
- blocked không lý do  -> script báo vi phạm.
- done thiếu quality gate -> không được chuyển (reviewer chặn).
- ID không tái sử dụng.

Thời điểm bắt buộc chạy script: nhận task / nộp review / done /
blocked / tạo-hủy task / cuối mỗi session (cùng lúc với handoff).

36. MEDIA GENERATION GATES (bổ sung cho dự án SINH MEDIA)
======================================================================

Chuẩn gốc viết cho dự án phần mềm thuần. Dự án sinh ảnh/video/audio
có thêm loại tài nguyên tiêu hao (quota tài khoản, tiền API) và loại
output non-deterministic (take). Bổ sung các gate sau:

MONEY GATE
----------
Mọi lệnh generate tiêu quota/tiền phải qua stage-gate:
agent tạo DRAFT kèm giá ước tính -> người bấm mới bắn.
Chế độ auto chỉ trong ngân sách đã reserve trước, không hoàn khi fail.
TUYỆT ĐỐI không auto-retry lệnh generate trả phí.

TAKE KHÁC TEST
--------------
- Take = attempt non-deterministic CÓ CHỦ ĐÍCH từ cùng input -> retake hợp lệ.
- Idempotency = dedupe-on-submission (chống double-spend khi replay).
Hai khái niệm, hai cơ chế. Không dùng chung một khóa.

AUTHORITY ORDER (canon)
-----------------------
HUMAN PIN > SERIES CANON > APPROVED ASSET > CONTINUITY OBSERVED
> SHOT REFERENCE > STYLE REFERENCE > LLM INFERENCE.
Không commit observed state khi QC chưa PASS.
Không cập nhật Canon từ output lỗi của model.

CORPUS BẮT BUỘC
---------------
Mọi generation ghi reference_usage + kết quả QC/verdict.
Corpus là ground-truth để eval scorer, calibrate router,
xác minh field DSL nào provider thật sự honor.

CAPABILITY LÀ DATA
------------------
Giới hạn/khả năng provider nằm trong provider-profiles/*.json
(có runtime_verified). Cấm hardcode vào business logic.
Guard CI: no-hardcoded-model-capabilities.

QC HUMAN-IN-LOOP TRƯỚC
----------------------
Máy chấm là GỢI Ý kèm bằng chứng; người bấm PASS/RETAKE.
Auto chỉ mở per failure-class sau pre-study đo precision/recall
trên corpus có nhãn người.
